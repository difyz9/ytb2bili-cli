## 1. 背景与现状

两个本地 CLI 项目高度互补，能力几乎无重叠、局限互为镜像：

| 维度 | ytb2bili-cli（项目一） | social-auto-upload-cli / 千帆云递（项目二） |
|---|---|---|
| 语言 | Go（urfave/cli → cobra 迁移中） | Python 3.10+（Typer + Rich + Playwright） |
| 定位 | 内容**获取 + 加工**管线 | 内容**多平台分发**网络 |
| 上游能力 | YouTube 搜索（InnerTube）、yt-dlp 下载、Bcut ASR 转录、DeepSeek 批量翻译、IndexTTS2 配音/音画同步、AI 元数据生成、频道监控（RSS）、任务队列、飞书集成、HTTP API | — |
| 分发能力 | **仅 B 站**（API 直传 + 字幕异步上传 + 审核监听） | **17 平台**一键发布（扫码/Cookie 双登录、定时发布、视频+图集、素材库、草稿箱、发布历史统计、标签管理、创作中心） |
| 核心资产 | 完整加工管线 + B站官方 API 链路 | 17 平台 Playwright 自动化引擎 + 多平台账号体系（SQLite） |
| 局限 | 加工完只能发一个平台 | 没有内容获取/加工能力，只能发本地现成文件 |

**合并的本质**：把「加工能力」和「分发能力」用一条命令串起来 —— 一次加工、多点分发。两者都不是平台化产品，是 CLI 工具，合并必须保持 CLI 的简单直接，**不做 Web 化、不做 SaaS、不做微服务**。

---

## 2. 合并的业务目标（结论先行）

**一句话目标**：让用户用一条命令完成「从 YouTube 等源站获取内容 → 自动加工（下载/转录/翻译/配音/元数据）→ 按平台差异适配 → 一键分发到多个平台」。

拆成 4 个可衡量的子目标：

| # | 业务目标 | 现状痛点 | 合并后 |
|---|---|---|---|
| G1 | **搬运管线 + 多平台分发一体化** | 加工产物是 ytb2bili 内部格式，要发其他平台需人工搬运文件、重写标题/简介/标签 | 管线产物标准化为「发布包」，直接作为分发输入，全程一条命令 |
| G2 | **一次加工、N 次分发** | 同一视频每发一个平台就要重复一次人工上传操作 | 一次加工生成平台适配的 N 套投稿内容，一键分发 |
| G3 | **全局去重** | 去重只覆盖 B 站维度（ytb2bili history），换平台会重复搬运/重复发布 | 以内容指纹为唯一依据，跨平台去重（源站去重 + 各平台发布去重） |
| G4 | **账号与数据资产统一** | B站登录两套并存、两套 history、两套配置，数据割裂 | 单一凭据存储、单一历史库、单一配置入口，老数据无损迁移 |

**明确不做**：不做 Web UI 合并、不做平台化改造、不做多用户系统。合并的验收标准是「CLI 用起来更顺」，不是「系统更庞大」。

## 3. 产品定位与用户故事

### 3.1 定位

> **千帆云递（QianFan Sync）**：一款面向内容搬运与多平台运营的 CLI 工具 —— 从 YouTube 等源站获取内容，自动加工成适合国内平台的内容形态，一键分发到全网。

- 目标用户：独立创作者 / 搬运工 / 多平台运营者 / 小型 MCN，单人多账号运营场景。
- 价值主张：**「一条命令，从源站到全网」**。用户只需要给 URL，其余全部自动。
- 产品形态：单一 CLI 入口（命令名待定，见 §8 开放问题 Q2），兼容旧命令别名（`y2b` / `sau` 至少保留一个迁移期）。

### 3.2 用户故事（5 个）

| ID | 用户故事 | 验收要点 |
|---|---|---|
| US1 | 作为**搬运创作者**，我希望粘贴一个 YouTube 链接就能自动完成「下载 → 转录 → 翻译 → AI 元数据 → 发布」，这样我不用记住 7 个步骤 | 单命令端到端；dry-run 可预览全流程；每步可跳过（--skip-translate 等语义保留） |
| US2 | 作为**多平台运营者**，我希望同一视频按平台规范（标题长度、标签数量、封面尺寸、B站分区/创作声明、抖音热点）自动适配后分发到多个平台，这样每个平台的内容都合规 | 一次加工产出 N 套平台适配投稿内容；发布前可预览每平台最终内容 |
| US3 | 作为**批量搬运者**，我希望同一视频重复执行命令不会在任何平台重复发布，这样我能放心批量跑 | 内容指纹去重：重复执行零重复发布；已发布平台状态可见 |
| US4 | 作为**定时运营者**，我希望加工产物能进入各平台定时发布队列，这样我不用守着电脑准点操作 | 发布包可指定发布时间；分发失败可重试，不产生重复 |
| US5 | 作为**风险敏感用户**，我希望发布前能完整预览每个平台将要提交的内容，这样我不会发错平台或发错文案 | --dry-run 在管线与分发全链路都强制禁止真实发布；预览输出与真实发布内容一致 |

## 4. 功能范围与优先级

### 4.0 核心抽象：发布包（Publish Package）

合并的关键不在「把两个 CLI 塞进一个入口」，而在**中间产物标准化**。管线产物必须收敛为一个可分发、可重放、可去重的「发布包」：

```
publish-package/
├── manifest.json        # 源URL、内容指纹、语言、加工时间、步骤记录
├── video.mp4            # 成品视频（配音版/原声版可选）
├── cover.jpg            # 封面
├── subtitle.zh.srt      # 中文字幕（可上传的平台用）
├── title.txt            # AI 生成标题（原始版）
├── desc.txt             # AI 生成简介
└── tags.txt             # AI 生成标签
```

- 发布包是 P0 数据契约，两个项目的模块围绕它对接，互不侵入对方内部实现。
- 发布时由「平台适配层」把发布包渲染为各平台格式（标题截断、标签拆分、封面裁剪、分区映射等）。
- 内容指纹 = f(源视频 ID + 成品文件哈希)，用于全局去重。

### 4.1 P0 —— 合并必须（不做则合并无意义）

| # | 功能 | 说明 | 验收要点 |
|---|---|---|---|
| P0-1 | 统一 CLI 入口与命令树 | 一个命令入口覆盖两个项目的全部命令；提供 `y2b`/`sau` 兼容别名或迁移说明 | `--help` 全量可查；旧命令可用 |
| P0-2 | 管线产物标准化为发布包 | ytb2bili 管线各步骤（download/transcribe/translate/metadata/audio-sync）产物统一落为发布包结构 | manifest.json 完整；产物路径可预测 |
| P0-3 | 多平台发布目标接入（核心 5 平台：**B站、抖音、小红书、快手、视频号**） | 发布包可直接投递到核心平台；B站走 ytb2bili 现有 API 直传链路（见 §5） | 端到端一条命令发布到 ≥3 平台（dry-run 验证） |
| P0-4 | 平台适配层（元数据多平台渲染） | 标题/简介/标签/封面按平台规范自动适配；平台规格规则集中维护、可配置 | 每平台预览内容符合该平台规范 |
| P0-5 | 全局去重与统一发布历史 | 内容指纹去重（源站维度 + 平台维度）；两套历史合并为单一记录 | 重复执行零重复发布；历史可查、可导出 |
| P0-6 | 账号体系统一 | B站登录合一（以 ytb2bili 扫码为准）；sau 各平台账号（扫码/Cookie）沿用并纳入统一管理 | 一处登录、处处可用；凭据不丢 |
| P0-7 | 安全红线语义统一 | `--dry-run` 在管线与分发全链路都强制禁止任何真实发布；`--skip-translate` 等既有安全参数语义不变 | 自动化测试覆盖：dry-run 零真实副作用 |
| P0-8 | 数据迁移脚本 | sau SQLite（账号/素材/草稿/历史/标签）+ ytb2bili data/（history/cookies/订阅）→ 新库 | 100% 迁移、失败项有报告、可回滚 |

### 4.2 P1 —— 增强（合并后价值放大器）

| # | 功能 | 说明 |
|---|---|---|
| P1-1 | sau 其余 12 平台接入验证 | 核心链路打通后，剩余平台（百家号/TikTok/腾讯视频/爱奇艺/微博/支付宝/头条/知乎/CSDN/VIVO/公众号等）逐一通过发布包验证，成本主要在测试不在开发 |
| P1-2 | 定时发布联动 | 发布包指定 `--schedule`，各平台定时发布（沿用 sau 能力）；sau `daemon` 定时发布守护进程（当前未完成）视需要补齐 |
| P1-3 | 草稿箱联动 | 加工产物可直接存草稿，人工确认后批量发布（发布包 ↔ sau 草稿互转） |
| P1-4 | 频道监控 → 自动分发 | RSS 发现新视频 → 自动入管线 → 产物进待发布队列，半自动（人工确认后分发） |
| P1-5 | 素材库与标签管理统一 | 管线下载产物自动进素材库；账号标签体系保留 |
| P1-6 | 跨平台统计 | 发布历史统计覆盖全部平台 + B站字幕/审核状态回传展示 |
| P1-7 | 图集发布 | 视频封面/关键帧生成图集，发布到图文平台（小红书/微博等 6 平台） |

### 4.3 P2 —— 暂不合并 / 明确不做（本阶段）

| # | 功能 | 结论与理由 |
|---|---|---|
| P2-1 | YouTube 发布（sau youtube 平台） | **保留现状不纳入合并验证**。价值与风险不成正比：国内环境 Google 账号登录脆弱、风控风险高、目标受众也在国内平台。代码保留，不做联动、不投入 |
| P2-2 | CloakBrowser 反检测重构 | 沿用 sau 现状即可，合并阶段不重构、不迁移实现 |
| P2-3 | 图文内容加工（视频 → 图文笔记生成） | 需 AI 抽帧 + 文案重组，复杂度高、价值待验证，暂缓 |
| P2-4 | 飞书集成 / HTTP 服务 / 浏览器扩展现代化 | ytb2bili 已有能力全部保留（不动、不删），但不在合并范围内扩展 |
| P2-5 | Web UI / 多用户 / 平台化 | 明确不做，违背「CLI 合并、务实第一」原则 |

## 5. 功能重叠分析（B站 / YouTube）

两个项目真正重叠的平台只有 **B站** 和 **YouTube**，且重叠形态完全不同。逐一给结论：

### 5.1 B站：以 ytb2bili 的 API 直传链路为准（sau 实现降级为兜底）

| 维度 | ytb2bili（API 直传） | sau bilibili（Playwright 自动化） |
|---|---|---|
| 方式 | 官方接口直传（登录 → 上传 → BVID） | 浏览器模拟操作 |
| 速度/稳定性 | 快、稳定 | 慢、受页面改版影响 |
| 字幕 | ✅ 异步上传 + 审核监听（30s 轮询 / 24h 等待） | ❌ 无 |
| 审核状态机 | ✅ 完整 | ❌ 无 |
| 独有能力 | 分区 tid、合集、创作声明 | 定时发布、AI 内容声明、转载来源参数 |

**结论（业务视角）**：
1. **P0 发布链路统一走 ytb2bili API 直传**。理由：API 直传是合并后唯一具备「字幕上传 + 审核状态回传」能力的 B站链路，而这正是搬运场景的刚需；浏览器自动化在速度、稳定性、维护成本上全面劣势。
2. sau 的 bilibili 实现**保留代码、不再扩展**，仅在 API 链路故障时作为手动兜底通道（文档注明），不参与自动化主流程。
3. sau 独有参数（创作声明/AI 声明/转载来源/定时）中，**转载来源与创作声明**由平台适配层（P0-4）在 API 直传中补齐；**定时发布**由 P1-2 覆盖。参数不丢失。

### 5.2 YouTube：方向相反，无取舍，只有一个边界问题

- ytb2bili 是 YouTube 的**消费方**（InnerTube 搜索 + yt-dlp 下载）；sau 是 YouTube 的**发布方**（Playwright 上传）。
- 两者不冲突、不重复，合并后自然共存：ytb2bili 负责「从 YouTube 拿」，sau 负责「发到 YouTube」（后者按 §4.3 P2-1 定位为保留现状）。
- **唯一需明确边界**：内容指纹与「源站」判定 —— 从 YouTube 下载的视频再发布到 YouTube 属于搬运回源站，合并后默认去重规则应允许（跨平台搬运合法场景），但需在配置中可开关。

### 5.3 其他隐性重叠

| 项 | 现状 | 合并处理 |
|---|---|---|
| B站登录 | 两套并存（ytb2bili data/cookies vs sau SQLite） | 统一凭据存储（P0-6） |
| 发布历史 | 两套独立（data/history vs SQLite history） | 统一历史库（P0-5），BVID/平台ID 双记录 |
| 配置 | config.yaml + 环境变量 vs sau config（SQLite） | 单一配置入口，三层合并（默认值 < 配置文件 < 环境变量/CLI 参数），优先级文档化 |

## 6. 非功能需求

| 类别 | 需求 | 验收要点 |
|---|---|---|
| CLI 体验 | 命令树扁平可发现；进度输出统一（Rich/日志一致）；`--json` 全命令可用 | `--help` 全量；`--json` 输出可被脚本消费 |
| 安全 | 任何环节 `--dry-run` 均零真实副作用；Cookie/凭据加密存储、日志脱敏、不落 README | 自动化测试：dry-run 全链路零副作用 |
| 幂等与去重 | 发布幂等：同一发布包 + 同一平台 + 同一指纹 → 不重复发布；失败重试不产生脏数据 | 重复执行零重复发布（AC2） |
| 数据迁移 | 账号 Cookie、素材、草稿、历史、标签 100% 迁移；失败项显式报告；迁移前自动备份 | 迁移报告可审计；可回滚 |
| 配置兼容 | 旧环境变量（DEEPSEEK_API_KEY/YOUTUBE_COOKIES 等）与旧配置自动识别，不要求用户重配 | 老配置零手工迁移 |
| 平台适配维护 | 平台规格（标题长度/标签数/封面尺寸/分区）集中为规则库，可配置可更新，避免散落各平台代码 | 规则库独立文件/模块，文档化 |
| 可靠性 | 管线任一环节失败可断点续跑（复用产物）；分发部分失败可单独重试 | 断点续跑不重复加工；部分失败可重试 |

## 7. 验收标准（可量化）

合并成功的判定标准 —— **全部 P0 项通过即为合并成功**，P1 为发布后迭代项：

| # | 验收标准 | 衡量方式 | 目标值 |
|---|---|---|---|
| AC1 | 端到端一键发布：一条命令完成「YouTube URL → 加工 → ≥3 个核心平台发布」 | dry-run 全链路演练 + 真实发布抽样 | 单命令可达；dry-run 100% 可预览 |
| AC2 | 全局去重：同一视频重复执行命令 | 指纹去重测试 | 重复执行零重复发布（0 条重复记录） |
| AC3 | 兼容回归：ytb2bili 现有命令（search/submit/channel/auto/subtitle 等）行为与合并前一致 | 命令级回归测试 | 回归通过率 100% |
| AC4 | 数据迁移：账号/素材/草稿/历史/标签无损迁移 | 迁移脚本 + 抽样核对 | 迁移率 100%；失败项 100% 报告 |
| AC5 | 发布成功率：核心平台不低于合并前 sau 单独使用水平 | 以 sau 历史统计为基线对比 | 成功率 ≥ 基线（如 ≥95%） |
| AC6 | 效率提升：一次加工 N≥3 平台分发的用户操作步骤 | 操作步骤对比（合并前两项目接力 vs 合并后单命令） | 操作步骤减少 ≥ 50% |
| AC7 | 安全红线：dry-run 全链路零真实发布 | 自动化测试（管线 + 分发 + 定时场景） | 零真实副作用 |
| AC8 | 发布包契约：管线产物 → 分发输入全程无人工格式转换 | 端到端冒烟测试 | 无人工干预 |

**P0 功能验收检查表（交付 Tester 用）**：P0-1 命令全量可用；P0-2 manifest 契约完整；P0-3 核心 5 平台发布成功；P0-4 平台适配预览合规；P0-5 去重 + 历史统一；P0-6 凭据统一；P0-7 dry-run 安全；P0-8 数据迁移 100%。

| Q5 | **自动化合规边界**：多平台自动发布的风控/封号风险、Cookie 维护成本 | 文档明示风险 + dry-run 默认安全模式；由用户自行承担账号风险 | 低 —— 影响信任与免责 |
| Q6 | **图集/图文加工**（视频 → 图文）是否纳入 | P2 暂缓，用户确认后再启动 | 低 |
| Q7 | **仓库与发布策略**：合并进哪个仓库、版本号策略（v1.0?）、发布渠道（二进制/Homebrew/pip） | 建议以 Go 主仓库为主（若选型 Go），Python 引擎作为内嵌资产；版本统一为合并后 v1.0 | 低 —— 影响交付物形态 |

**阻塞性决策**（Backend 落地方案前必须确认）：Q1（选型）、Q2（命名）、Q3（平台范围）。其余可并行。
