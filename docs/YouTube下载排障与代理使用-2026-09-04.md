# YouTube 下载排障与代理使用调研记录（2026-09-04）

> 本文档完整记录一次「YouTube 下载持续失败」的排查过程、根因、代码改动与验证结论，
> 供后续自行阅读与使用。所有命令均可直接复制执行；涉及敏感信息处已用占位符标注。

## 1. 背景与原始问题

- **场景**：ytb2bili-cli（`ytb`）daemon 批量搬运 YouTube → Bilibili。系统日志显示大量任务卡死在 `download` 步骤。
- **队列现状**（2026-09-04 排查时）：总任务 2041，已完成 417，**失败 1624**，失败全部为下载步骤 `exit status 1`。
- **原始提问**：能否通过代理访问 YouTube、下载视频？（附一张 SOCKS5 代理表，示例行：
  `203533 | SOCKS5 | 154.222.46.2 | 62813 | YNtVtMrf | NedyYDqp | ... | HK`）
- **追加信息**：提供了最新 cookie 导出文件 `www.youtube.com_cookies.txt`。

## 2. TL;DR（结论速览）

| # | 结论 | 说明 |
|---|------|------|
| 1 | **项目本身支持代理下载**（本次已补内置支持） | 下载走 yt-dlp，原生支持 socks5/http/https；已加 `youtube_proxy` 配置 + `--proxy` 透传，**仅作用于 YouTube 流量**，B站/翻译不走代理 |
| 2 | **1624 个失败的真正根因 = cookie 缺 SID，不是 IP 被拉黑、不是必须代理** | daemon 默认 cookie 文件是 Chrome 扩展推送的「半登录态」：有 `__Secure-3PSID` 但**无 `SID`** → YouTube 判定不可信 → 媒体数据阶段 403 / bot 验证 |
| 3 | **代理实测能下载**（本会话 14:35 与 15:04-15:05 各成功一次完整下载） | 但该 HK 机房 IP 与 YouTube 风控是拉锯战：间歇性 bot 拦截、**渐进式单文件(itag 18) 403、DASH/HLS 分离流可通**、速度慢有卡顿 |
| 4 | **正确组合**：完整登录态 cookie（含 SID）+ 稳定出口（直连优先，代理备选） | 缺一不可；代理不是替代 cookie 的方案 |
| 5 | **当前遗留新阻塞**：DeepSeek / 腾讯 key 均失效 → translate/metadata 步骤跑不通 | daemon 已暂停，等有效 key 后再启动 |

## 3. 症状与初始证据

日志（`journalctl --user -u ytb-batch-loop`）中的典型失败，全部秒级失败、无重试价值：

```
ERROR: [youtube] tVpuGeukMsA: Sign in to confirm you're not a bot. Use --cookies-from-browser or --cookies ...
ERROR: unable to download video data: HTTP Error 403: Forbidden
ERROR: unable to download webpage: HTTP Error 429: Too Many Requests
❌ 下载失败: 下载失败: exit status 1
```

**关键观察**：失败发生得极快（数秒内），且错误类型在 403 / 429 / bot 验证之间切换——
这暗示「会话/凭证级」问题而非单纯网络波动。

## 4. 排查过程（方法论：逐层对照实验）

### 4.1 先确认「能不能直连 YouTube」

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://www.youtube.com/          # → 200
curl -6 -s -o /dev/null -w '%{http_code}\n' https://www.youtube.com/       # → 200（IPv6 也通）
```
结论：网页可达，IPv4/IPv6 均正常 → **不是断网**。

### 4.2 区分「网页/元数据」与「真实媒体数据下载」

用 yt-dlp 分开测两类请求（这是本次排查最重要的一步）：

```bash
# 轻量：仅取元数据（走网页/player API）
yt-dlp --cookies <file> --dump-json --no-download <URL>        # 成功

# 重量：真实拉媒体数据
yt-dlp --cookies <file> -f '18/worst' -o /tmp/t.%(ext)s <URL>  # → ERROR: unable to download video data: HTTP Error 403
```

**结论**：元数据 OK、媒体数据 403 → 问题定位在 googlevideo 媒体 CDN 阶段。

### 4.3 对照实验矩阵（决定性证据）

对同一小视频（`jNQXAC9IVRw`）用不同 cookie / 代理 / 出口组合实测：

| Cookie 文件 | 出口 | 媒体下载 | 解读 |
|---|---|---|---|
| `data/cookies/youtube_cookies_from_meta.txt`（meta 推送，**无 SID**） | 直连 | ❌ 403 | 半登录态被拒 |
| `www.youtube.com_cookies.txt`（14:32 导出，**含 SID**，2937B） | 直连 | ✅ 成功 | 完整登录态 → 放行 |
| 同上 | HK SOCKS5 代理 | ✅ 成功 | 代理本身可用 |
| 无 cookie | 直连 | ⚠ 时好时坏 | 匿名会话极不稳定 |

**根因确定**：同样的出口 IP，换 cookie 结果天差地别 → **是 cookie 完整性问题，不是 IP/代理问题**。

### 4.4 对比两个 cookie 文件差异（看破真相的一步）

```bash
awk -F'\t' '$6=="SID"{print "SID present"}' <file>   # 关键判据
```

- `www.youtube.com_cookies.txt`（可用版）：**有 `SID`**、`SSID`、`APISID`、`LOGIN_INFO` 等全套 ~22 行。
- `data/cookies/youtube_cookies_from_meta.txt`（失效版）：**无 SID**，只有 `__Secure-3PSID` 等 ~16 行。

`SID` 是 YouTube 登录会话的**核心身份 cookie**（httpOnly）。缺它 = 半登录态 =
YouTube 对媒体 CDN 按「不可信会话」处理 → 403 / bot 验证。

> 补充发现：`www.youtube.com_cookies.txt` 在 15:05 被再次覆盖导出后**又变成缺 SID 的 16 行版本**——
> 说明导出源会话不稳定。**每次导出后必须自查 SID 是否存在**（见 §8.1）。

## 8. 使用手册（自用速查）

### 8.1 Cookie 自查（每次重新导出后必做）

```bash
cd /home/guan/guan/code/ytb2bili-cli
# 必须输出 SID（且文件 ≥20 行、含 SSID/APISID/LOGIN_INFO 更佳）
awk -F'\t' '$6=="SID"{print "SID ✓"}' www.youtube.com_cookies.txt
wc -l www.youtube.com_cookies.txt
```

- 缺 SID → 重新从**已登录 YouTube 的浏览器**导出（登录态 cookie 导出工具），覆盖 `www.youtube.com_cookies.txt`。
- 导出源必须是真的登录账号会话，不是 headless/无头会话。
- 新版 ytb 会在缺 SID 时打印醒目告警，看到即处理。

### 8.2 快速验证下载是否正常

```bash
# 直连（首选）
env -u YOUTUBE_COOKIES ./ytb chain run download jNQXAC9IVRw   # 19s 小视频，几秒出结果
ls -la data/downloads/jNQXAC9IVRw/                            # 应出现 .mp4

# 走代理（备选/验证代理）
env -u YOUTUBE_COOKIES YOUTUBE_PROXY='socks5://user:pass@host:port' \
  ./ytb chain run download jNQXAC9IVRw
```

### 8.3 启用代理（永久配置）

编辑 `config.yaml`，取消注释并填：

```yaml
youtube_proxy: "socks5://YNtVtMrf:NedyYDqp@154.222.46.2:62813"
# 或 http://user:pass@host:port / https://...
```

然后重启 daemon。**注意**：代理仅影响 yt-dlp 相关步骤；不改任何脚本。

### 8.4 重启 / 运维命令

```bash
systemctl --user stop ytb-batch-loop     # 优雅停止（有挂起 bug，见 §9，可 kill -9）
systemctl --user start ytb-batch-loop    # 启动
journalctl --user -u ytb-batch-loop -f   # 实时日志
ytb daemon status                        # 心跳（状态/批次/当前任务）
ytb queue status / list                  # 队列统计 / 明细
ytb queue retry-failed                   # 手动重排队失败任务（修好根因后再用）
ytb task show <task_id>                  # 任务步骤状态定位
```

### 8.5 直接命令行下载（纯 yt-dlp，不经过 ytb 流程）

绕过项目流程直接用 yt-dlp 下载单条视频，用下面这条（**2026-09-04 实测通过**：19s 完成，
DASH 流 136+251 合并成功）：

```bash
# 账号密码顺序固定为 账号:密码（表格：账号=YNtVtMrf / 密码=NedyYDqp），别写反
# socks5h:// 表示域名也走代理解析（推荐）
yt-dlp \
  --proxy "socks5h://YNtVtMrf:NedyYDqp@154.222.46.2:62813" \
  --cookies ./www.youtube.com_cookies.txt \
  --impersonate chrome-116:windows-10 \
  --force-ipv4 \
  -f 'bestvideo+bestaudio/best' \
  --merge-output-format mp4 \
  "https://www.youtube.com/watch?v=<VIDEO_ID>"
```

**踩坑记录：**

1. **代理账号密码写反**是常见报错来源（`socks5h://账号:密码@地址:端口`）。
2. `--impersonate chrome-131:windows-10` 这类目标**依 yt-dlp 版本而定**，目标不存在会直接报错
   `Impersonate target ... is not available`。先查可用目标：
   ```bash
   yt-dlp --list-impersonate-targets   # 本机(yt-dlp 2026.07.04) Windows Chrome 最高 116，Chrome-131 只有 Android-14
   ```
   可用目标随版本更新而变，`yt-dlp -U` 升级后即解锁更新的目标。
3. `--impersonate` 能显著缓解缺 SID cookie 时的 bot 拦截（15:11 实测缺 SID 也下成功），
   但**不要依赖它替代完整 cookie**——含 SID 的完整登录态才是长期稳定解。
4. 常用附加参数：`-o '/路径/%(title)s.%(ext)s'` 指定输出目录；`-k` 保留分离的音视频流；
   `--limit-rate 2M` 限速；`--socket-timeout 30` 防卡死。
5. 只看格式列表不下载：`yt-dlp ... -F <URL>`。

## 9. 已知问题与后续建议

1. **daemon 优雅停机挂起**：`systemctl --user stop` 后进程收到 SIGTERM 打出
   `🛑 收到退出信号，结束循环` 但进程不退出（卡 `futex_wait`，等 15min+）。
   现状需 `kill -9 <pid>` 兜底。属既有问题（改动前即存在），建议另开任务排查 daemon 停止路径。
2. **meta cookie 刷新器持续产生缺 SID 文件**：`internal/download/cookies.go` 的
   `SaveCookiesFromMeta` 会把 Chrome 扩展推送的 meta 写入 `data/cookies/youtube_cookies_from_meta.txt`，
   该来源实测缺 SID。**根因在扩展导出端**（可能拿不到 httpOnly 的 SID），Go 侧只能加告警不能修复。
3. **代理选择建议**：该 HK 机房 SOCKS5 能用但**不稳定**（bot 拦截随请求量波动），且
   渐进式单文件格式被 403（DASH/HLS 可通，项目默认格式恰为 DASH，故可正常工作）。
   批量场景优先直连；代理留作直连被限时的备选，且需配合完整 cookie。
4. **请求节奏**：daemon 每 60s 一批 × 18 个搜索关键词 + 下载重试，高频请求会诱发
   googlevideo 对出口 IP 的媒体限流（表现为间歇 403）。注意不要让大量失败任务空转重试。
5. **`cookies.txt`（仓库根目录，已跟踪）** 在本次排查前就有未提交改动（追加了 bilibili cookies），与本次无关，未改动。

## 11. 一句话总结

> **下载失败的根因不是网络、不是代理，而是 cookie 缺 SID（半登录态）→ 403；
> 修复 = 使用含 SID 的完整登录 cookie（`youtube_cookies` 指向 `www.youtube.com_cookies.txt`）。
> 代理能力本次已内置（`youtube_proxy`），实测可用但不稳定，仅作备选。**
