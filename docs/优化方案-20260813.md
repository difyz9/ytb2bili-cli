# ytb2bili-cli 项目优化方案

> 日期：2026-08-13
> 目标：减少脚本依赖、收敛调度入口、提升稳定性

---

## 一、当前运行架构总览

```
┌─────────────────────────────────────────────────────────────────┐
│  systemd 用户服务（2 个）                                          │
│  ├─ ytb-batch-loop.service  → batch_loop.sh（主循环，持续运行）     │
│  └─ index-tts.service       → IndexTTS2 TTS 服务（配音后端）       │
├─────────────────────────────────────────────────────────────────┤
│  脚本层（15+ 个，散落 3 处）                                       │
│  ├─ 项目根目录: batch_loop.sh + 5 个历史 batch_*.sh（一次性任务）   │
│  ├─ scripts/: ytb2bili-auto-cron.sh + 3 个辅助脚本                │
│  └─ ~/.hermes/scripts/: 5 个 ytb2bili-*-cron.sh（旧路径，已失效）   │
├─────────────────────────────────────────────────────────────────┤
│  Go 二进制 ytb（唯一被直接调用的程序）                               │
│  ├─ auto 命令：搜索→评分→去重→入队→处理                             │
│  ├─ queue 命令：任务队列状态机                                     │
│  ├─ task 命令：单任务管理                                          │
│  └─ 其他：submit / channel / publish / subtitle / server          │
└─────────────────────────────────────────────────────────────────┘
```

## 二、当前存在的问题

### 问题 1：脚本数量失控（15+ 个，职责重叠）
| 位置 | 数量 | 问题 |
|------|-----:|------|
| 项目根目录 `batch_*.sh` | 6 | 5 个是一次性历史任务（Nicolai、Tech With Tim、重试批次），已完成使命但未清理 |
| `scripts/*.sh` | 4 | auto-cron 与 batch_loop 功能重叠；wait_* 脚本是临时补丁 |
| `~/.hermes/scripts/ytb2bili-*.sh` | 5 | **全部指向旧路径 `ytb2bili-go`**（现项目在 `ytb2bili-cli`），运行即失败，且 Hermes cron 中已无任务引用，纯僵尸文件 |

### 问题 2：调度入口分裂（三套机制并存）
1. **systemd 服务**（当前主用）：`batch_loop.sh` 无限循环
2. **Hermes cron 旧脚本**（已失效但文件还在）：auto-cron / channel-cron / worker-cron 等
3. **手动脚本**：`batch_retry.sh`、`batch_nicolai.sh` 等

→ 三套机制关键词各自维护（batch_loop 一套、auto-cron 一套、search.go 一套），**改关键词要同步 3 处**，极易漏改。

### 问题 3：batch_loop.sh 逻辑臃肿（职责全堆在 bash 里）
单脚本内混了：失败重试 → 遗留续跑 → 队列消费 → 关键词轮换 → 搜索搬运 → 队列统计 → 空转判断。bash 写业务逻辑，难以测试、难以排错、没有类型检查。

### 问题 4：无健康自检与自愈
- 之前实测：一个 35 分钟长视频 TTS 单并发合成卡 40+ 分钟，batch_loop 无感知（无超时/无进度告警）
- 失败任务（4 个）反复重试，可能无限堵队列
- 服务挂掉只能靠人工 `systemctl status` 发现

### 问题 5：配置/关键词分散
- 关键词：`search.go` StandardKeywords + `batch_loop.sh` KEYWORDS + `auto-cron.sh` KEYWORDS_*（三处）
- 搜索策略参数（评分器、上传日期、时长上限）硬编码在 `batch_loop.sh` 命令行里
- 改配置 = 改脚本 + 重启服务

### 问题 6：重启流程繁琐
改配置/关键词后，需要：等待当前任务完成 → 手动 restart systemd 服务（此前靠临时 wait_then_restart.sh 脚本）。

## 三、优化方案

### 方案核心：把调度逻辑下沉到 Go 二进制，脚本只留「入口」

```
现在:  systemd → batch_loop.sh(bash 逻辑) → ytb auto ...
目标:  systemd → ytb daemon（Go 内置循环，读 config.yaml）
```

### Step 1：新增 `ytb daemon` 子命令（核心改造）
在 Go 里实现 batch_loop.sh 的全部逻辑：
- **内置主循环**：关键词轮换、评分、去重、入队、串行处理
- **失败重试策略**：失败 N 次后标记"人工介入"不再自动重试（防止堵队列）
- **任务超时检测**：单任务超过阈值（如下载 30min / TTS 60min）自动 kill 重试
- **健康上报**：每批心跳写 `data/daemon/heartbeat.json`（批次号/时间/队列统计），systemd watchdog 可读
- **优雅重启**：收到 SIGTERM 后等当前任务完成再退出（配合 `systemctl reload` 或 restart）

### Step 2：关键词/配置收敛到单一来源
- 关键词统一进 `config.yaml`（`search.keywords` 段），`batch_loop.sh` 和 `search.go` 的 StandardKeywords 全部废弃/合并
- `daemon` 启动时从 config.yaml 读取：关键词列表、评分策略、上传日期、时长上限、每批视频数
- 改关键词 = 改 yaml + `systemctl --user restart`，不再碰脚本

### Step 3：清理脚本
| 操作 | 文件 |
|------|------|
| 🗑️ 删除 | `batch_carry.sh` `batch_nicolai.sh` `batch_nicolai_retry.sh` `batch_retry.sh` `batch_retry2.sh` `verify_after_batch.sh`（一次性任务已完成） |
| 🗑️ 删除 | `~/.hermes/scripts/ytb2bili-*-cron.sh` 5 个（旧路径僵尸文件） |
| 🗑️ 删除 | `scripts/wait_and_restart.sh` `scripts/wait_then_restart.sh`（临时补丁，daemon 自愈后不需要） |
| 📦 归档 | `scripts/ytb2bili-auto-cron.sh`（逻辑并入 daemon 后可删，或保留为参考） |
| ✅ 保留 | `scripts/refresh_youtube_cookies.sh`（工具类，非调度） |

最终脚本收敛为：**batch_loop.sh 删除，systemd 直接 ExecStart=`ytb daemon`**。

### Step 4：systemd 服务精简
```
[Service]
ExecStart=/home/guan/.local/bin/ytb daemon
Restart=always
RestartSec=15
# 不再需要 bash 包装
```

### Step 5：监控与告警（可选增强）
- daemon 心跳文件 + Hermes cron 每 10 分钟检查心跳新鲜度（>15min 未更新 → 飞书告警）
- 失败任务连续 N 次 → 飞书通知人工处理

## 四、预期收益

| 指标 | 现在 | 优化后 |
|------|------|--------|
| 调度脚本数量 | 15+ 个（3 处散落） | **1 个 systemd 服务** |
| 关键词维护 | 3 处同步 | **1 处（config.yaml）** |
| 任务卡死检测 | 无 | ✅ 超时自动 kill 重试 |
| 失败任务处理 | 无限重试堵队列 | ✅ 达阈值停止+告警 |
| 重启流程 | 等任务+手动/临时脚本 | ✅ systemd 优雅重启 |
| 可测试性 | bash 难测 | Go 单测覆盖调度逻辑 |

## 五、实施计划（建议顺序）

**风险控制**：P0 开发期间 batch_loop.sh 保持运行，daemon 测试通过后再切换，零停机。
